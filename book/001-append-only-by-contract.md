# 只追加是一份合同

写作纪律总被写成礼貌请求：「动手前先读一遍磁盘，别覆盖别人刚改的字。」

场景：一个 agent 每天往同一份摘记文件里追加。它攒了三十条，靠的全是纪律——每次动手前先读文件、找到末尾、再追加。作者不在场的时候，另一个 session（同一套存储上并发的另一个会话）也在写同一个文件。

只熟 matt skills 的那位读者，做法是真有的：writing-fragments 的 Writing rhythm 就是这么写的——静默追加、每次写前从磁盘重读、永不整文件覆盖。它管用。但它是**约定**，而约定的代价是它只在「大家同时守约」时成立：两个人各自读完，各自追加，后写的那个把先写的抹掉，没人报错。这条约定把正确性押在纪律上，而纪律不是运行时能保证的东西。

durable（pi 的耐用运行时）把它换成合同。transcript（一条会话的全部记录）里的 *entry*（一条不可变的记录）一旦 *commit*（一次原子写）就不可变——不是「不许改」，是运行时里根本没有「改」这个动作。ID 永不复用。commit 从**写入线**（mutation line，会话里那条唯一的写入通道，所有写排队从它过去）上串行通过。于是「后写覆盖前写」这个失败模式在存储层不存在：没有覆盖这个动作可调用。真需要删除或重排时，路径也还在，但它必须改写成一次 *document* 更新（document 是存在 transcript 旁边、在 commit 内改动的 typed JSON 状态）：你改的不是历史，是一份指向历史的意见。

行为示意——两个 session 同时往一条 conversation 里递东西：

- 单边：A 读文件（v3），B 读文件（v3），A 写 v4，B 写 v4（A 那份没了），日志安静。
- 组合：A 提交 entry #41，B 提交 entry #42——两条都是同一条 conversation（transcript 的作用域，durable 里没有 thread 这个词）里的记录；两次 commit 在写入线上排队，两条都在，顺序就是排队顺序。要「删掉」#41，落下的是**一次** document 更新——历史里 #41 仍在，document 说它被排除。

何时别用：这份合同换来的东西是「历史不可改写」，代价是改写不便宜——删一条、改一条、重排一条，都要自己造出 document 那一层并维护视图（durable 没有会话级的可回退 document，历史版本的可见性是应用层自己拼的事）。只有一个作者、一次一个 session 的场景，纪律够用，别为不会发生的并发上这套机器。另一条：不可变意味着错误也留档，写错了不能涂改，只能追加一条更正——把「错的东西还留在那儿」当成产品不可接受的事，就别选它。

append-only 从纪律变成合同，差别不在严格程度，在**没有谁能违约**。
