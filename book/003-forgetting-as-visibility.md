# 遗忘即可见性

清上下文这个动作，在模型这边看着像删除，在存储那边其实是一次写入。

场景：一个跑了几天的会话，transcript（会话的全部记录）长到逼近 smart zone（模型还敏锐的那个窗口）。人或 agent 决定清一次上下文。

单边读者的做法是真实的：`/clear`，或者 handoff——把旧内容压成一份文件，然后「旧的就没了」。那份文件是留给你读的备忘录，原文只活在那一次会话里，会话一结束就真没了。这套做法把遗忘理解成一个减法：内容少了，行少了，人能一口气读完。它也确实能做到——因为它做的就是把东西弄没。

durable（pi 的耐用运行时）里遗忘是一次加法。`reset()` 落地的是两条事实：一条 `pi.reset` entry（一条不可变的记录）进历史，加上 head（指向「当前算作上下文的那个窗口」的游标）挪到新位置——原条目一条不少。模型看不见的那部分仍然可读：document（存在 transcript 旁边、在一次原子写里改动的 typed JSON 状态）没有被抹掉，`documentState`——会话读 document 的那个方法——照样读得到；历史里躺着那条 reset。底下有个更根本的分工：transcript 是**事实**，head 是「当前算作上下文的那个窗口」，这是两张纸。遗忘改的是窗口那张，不是事实那张。durable 从不删 entry——那个动词不存在——所以「模型忘了」和「存储忘了」是两个独立事件。

行为示意——同一个会话，清之前与清之后，看三样东西：

- 模型看得见的上下文：少了。
- 原有 entry 条数：一条不少；总条数多出一条 `pi.reset`。
- 扫一遍历史：那条 reset 本身就是一条可读的记录——什么时候清的、清到哪里，事后查得到。
- 隔一天有人问「最早那条需求是怎么不在上下文里的」：单边那边没有任何可查的东西，只能凭记忆；组合那边扫出那条 `pi.reset`，于是知道不是没发生过，是当时被移出了窗口。

单边那边只有第一行有数。第二、第三行没有可比对象，原文已经不存在了。

何时别用：遗忘可见不免费——历史只增不减，存储与扫描成本单调上升，你得自己决定什么时候把一段过去归档成一次真正的放弃。还有一条边界要记住：durable 没有会话级的可回退 document，「回看任意历史版本」不是存储交付的成品，是应用层自己拼的事。场景是一次性的、永远不会被追责的输出（草稿、实验），把可溯源的义务背到底只是负担；反过来，任何需要被审计、需要解释「当时为什么这么决定」的会话，别用真会删东西的方案去清。

forgetting as visibility——忘掉内容不是把内容弄没，是做一次看得见的切割。
