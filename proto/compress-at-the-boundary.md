# 边界压缩

省 token 的动作，本身要花 token。

**场景**。会话跑了三小时，上下文逼近 *smart zone*（模型还能敏锐推理的窗口，约 150k token），模型开始答得含糊。你压了一次，继续写。四小时后回看：压缩那几十秒里定下的两个决定，在下一段的开头从来没出现过——不是被改掉，是没到过。

**天真做法为什么不够**。单边读者的答案是 ask-matt 那条纪律：逼近 *smart zone* 就 *compaction*（压缩：把旧条目总结成一条摘要，原文仍在存储里，只是不再进上下文）。它把压缩当清理房间：快满了就扫一下。但压缩不是本地回收，它是一次**生成**。每次 attempt（一次尝试）都付一次总结请求，哪怕摘要最后用不上；摘要反映的是**选段那一刻**的上下文——压缩期间落的写入会被丢掉、head 标记会被撤销（*entry*（记录：一条不可改写的条目）上的标记值，决定模型看得到多少历史），文档原话是「Place such writes before compacting」。压缩之间还互不协调，谁生效由边界决定。所以「什么时候压」不是资源问题，是时序问题。

**组合机制**。另一侧已经给了时机：相位边界（phase boundary）的五个选项里本来就有 compact（Continue / clear / handoff / subagent / compact）。运行时的时序事实补上了**为什么边界压得住**：边界是「没有在飞的写入」的时刻，阈值是「资源快没了」的时刻。前者选段稳定，后者不稳定。于是队列反过来排——**边界压缩是策略，阈值压缩降级成兜底**（后台阈值压缩是保险丝，不是决定）。

还有一处别扭：上下文小于 keepRecentTokens（compaction 的一个阈值设置项，默认 20k）时什么都不会压，这时 overflow 可能先于任何阈值压缩到来。「我设了阈值所以安全」是假的。

**行为示意**。

```
边界压缩
  相位结束 → 没有在飞的写入 → compact(reason: manual)
    ├ 选段稳定，摘要不 stale
    ├ 没有写入可丢
    └ 下一相位从干净上下文起

阈值压缩
  写到一半，阈值到了 → compact(reason: threshold)，同时 edit 正在落盘
    ├ 摘要只反映选段时的上下文，那两笔 edit 被丢
    ├ head 标记被撤销
    └ 摘要 stale，再付一次总结请求
```

**何时不适用**。探索阶段：会话还在挖碎片、什么都没结晶，这时没有「已完成的写入」要保护，随手压的损失近乎零——为尊重边界硬等一个仪式性的相位结束，只是把窗口留给一个已经变钝的模型。单边的「满了就扫」在这一段是对的，而这一段的长度常常是整个 effort 的大半。

**回扣**。边界压缩：压缩的时机不是资源问题，是时序问题——压在没人写字的时刻，不压在没空间了的时刻。
