# 上下文经济学 · 候选清单（wayfinder #11）

读法同 [`notes/记忆与延续.md`](<记忆与延续.md>)：一条一个摘记，六栏照 [#11](https://github.com/JoeWest9966/md/issues/11)；主轴恒为本轴，次轴按需，缺次轴时写一句为什么。

---

**01 · 每次尝试都要付钱**

- 一句话角度：摘要每次尝试都付一遍钱，即使最后被判定作废
- 主轴：上下文经济学
- 次轴：记忆与延续（作废的那份落在历史里）
- 候选 leading word：every attempt pays
- 反直觉点在哪：以为压缩是「跑一次、得一份摘要」；实际并发压缩按切割位置判 stale，先跑完的那份照付钱然后被丢掉——**花钱与产出在这块是分开计量的**
- 单边做法是谁：matt 的 `/compact`（一次调用一次花，没有作废也没有重付）

---

**02 · 压缩会吃掉并发写**

- 一句话角度：压缩进行中，应用的 edit / head 写入可能丢失或被撤销
- 主轴：上下文经济学
- 次轴：记忆与延续（丢的是对历史可见性的编辑）
- 候选 leading word：compaction eats edits
- 反直觉点在哪：以为压缩只是「换个 head」，只影响上下文、不影响数据；实际它以压缩为轴，把窗口内对 head / edits 的写入一并吞掉——省钱的机制在别处收费
- 单边做法是谁：matt 的 handoff + compact 组合（先落盘再压，默认落盘了就不会被动）

---

**03 · 看不见的那一半**

- 一句话角度：结构化输出、嵌套调用的结果、工具的 details——三条不进 transcript 的通道
- 主轴：上下文经济学
- 次轴：验证与信任（程序拿得到、模型看不到，判据归谁）
- 候选 leading word：the invisible half
- 反直觉点在哪：以为「发生过的东西都会进上下文」；实际有三条正规通道专门不进——把它们当成遗漏就会重复造一遍，当成特性才知道省下来的正是注意力
- 单边做法是谁：matt 的 subagent 用法（结果回来了就贴进父上下文）

---

**04 · 指针不搬家**

- 一句话角度：context pointer 在运行时里的对应物，是「结论不进上下文、只留一条可取的路径」
- 主轴：上下文经济学
- 次轴：委派与并发（指针是代理之间唯一的通讯方式）
- 候选 leading word：pointer, not payload
- 反直觉点在哪：以为交接质量取决于摘要写得多全；实际密度反过来——写全了就是搬家，写指针才是省；durable 侧同形的做法（结果不进 transcript、子账记在自己身上）把这条从写作技巧变成结构
- 单边做法是谁：matt 的 implement-spec / chief-of-staff（communication only via context pointers，靠提示词纪律）

---

**05 · 两段式发现**

- 一句话角度：deferred 工具用 B 米搜索 + 载入；省下的是常驻清单，付出的是「模型得先知道要搜」
- 主轴：上下文经济学
- 次轴：共同语言（搜得到与否取决于措辞）
- 候选 leading word：pay twice to find once
- 反直觉点在哪：以为把工具藏起来纯赚；实际代价是一段两段式发现流程，而且 codemode 的 section 里**不含** deferred 工具，模型得先想起来搜——省上下文这件事永远有人要付一次「想起来」
- 单边做法是谁：matt 的 skill 索引（38 个 skill 的 description 常驻，模型直接挑，不搜）

---

**06 · 按词检索，不按意思**

- 一句话角度：工具检索是本机 BM25 加三条朴素词干规则，不是语义搜索
- 主轴：上下文经济学
- 次轴：共同语言（命名决定可检索性）
- 候选 leading word：search by word, not meaning
- 反直觉点在哪：以为「搜一下工具」是理解意图；实际它在按字面匹配——于是**词汇表就是索引**，改一个词名等于改一次召回率
- 单边做法是谁：matt 的 ask-matt 路由（靠人读表，表是人维护的）

**07 · 装得下才算知道**

- 一句话角度：`outputLimits` 默认 50 KiB / 2000 行 / `retain: "head"`——截断策略就是「模型知道什么」的上界
- 主轴：上下文经济学
- 次轴：验证与信任（被截掉的那部分是证据）
- 候选 leading word：what fits is what is known
- 反直觉点在哪：以为截断只是显示问题；实际尾巴就是模型看到的全部，而且截断规则（行 / 字节先到先得、永不返回半行）是经济决策——诊断一个 bug 时，最有用的那几行常在尾巴上
- 单边做法是谁：matt 的 diagnosing-bugs（把全量输出贴进对话，代价花在上下文里）

**08 · 工具清单要花 token**

- 一句话角度：codemode 每个会话要在 token 预算内把工具清单写成 TS 声明
- 主轴：上下文经济学
- 次轴：共同语言（清单的写法就是词汇表的写法）
- 候选 leading word：the catalog costs tokens
- 反直觉点在哪：以为工具「装上就有」；实际在 code mode 里，能力清单占的是一份按会话计的预算，超了就被截断——「有什么能力」本身花上下文
- 单边做法是谁：matt 的 skill 描述（也占 context，但没有预算计量这一栏）

**09 · 只重发增量**

- 一句话角度：system prompt 的 section 变更以位置型 entry 存进 transcript，只重发变更部分
- 主轴：上下文经济学
- 次轴：记忆与延续（变更的痕迹落在历史里）
- 候选 leading word：resend the delta
- 反直觉点在哪：以为改系统提示 = 下一次请求重发整份提示；实际它只重发差值，为的是保住 provider 侧的 prompt 缓存——省的不只是 token，是那一整段重算
- 单边做法是谁：matt 的 AGENTS.md / SKILL.md（每次全量读取、全量进上下文）

**10 · 一行会变的字打掉整个缓存**

- 一句话角度：section 输出每次不同（比如当前时间）会主动打掉缓存
- 主轴：上下文经济学
- 次轴：记忆与延续（这次 miss 就是历史的一次分叉）
- 候选 leading word：one changing line costs the cache
- 反直觉点在哪：以为「写一句时间戳」是零成本的贴心；实际它让整段前缀失去可缓存性——不稳定的一个字，价格是一整个前缀
- 单边做法是谁：matt 的 setup-\*（把环境变量与规则写死一次，稳定是默认）

**11 · 三个花钱旋钮**

- 一句话角度：`reserveTokens` / `keepRecentTokens` / `backgroundTokens` 决定压缩的花钱节奏
- 主轴：上下文经济学
- 次轴：—（机制只落在本轴：压缩阈值的三个设置项）
- 候选 leading word：three dials of spend
- 反直觉点在哪：以为「上下文不够就压」是一个自动行为；实际它是三个阈值做的连续决策，旋钮位置直接换算成钱与卡顿
- 单边做法是谁：matt 的 smart zone（一个 150k 的坎，到了就手动 compact）

**12 · 没有总账**

- 一句话角度：usage 按会话记账；跨会话的总额不存在，子树求和要应用自己扫
- 主轴：上下文经济学
- 次轴：委派与并发（子树是并发产物）
- 候选 leading word：no global ledger
- 反直觉点在哪：以为 `harness.usage()` 是存储里的计数器；实际是现算的求和——账本的单位是会话，不是项目
- 单边做法是谁：matt 的 `claude --bg`（一个进程一笔账，汇总靠人）

**13 · 失败也上账单**

- 一句话角度：失败与中止的尝试照样计费；而子会话的账**不能**在工具结果里再报一次，否则双计
- 主轴：上下文经济学
- 次轴：验证与信任（钱花了不等于证据到手）
- 候选 leading word：spend without evidence
- 反直觉点在哪：以为记账是为了记「做成了的事」；实际它记的是「花了的事」，而且第一个坑不是漏记，是重复记——账本的正确性靠一条「谁花的归谁」的规矩
- 单边做法是谁：matt 的 pr（证据分级只报成功的那部分，花掉的成本不进汇报）

**14 · 前沿得有个第二个家**

- 一句话角度：implement-spec 这种长跑，把「还差哪几张票、哪几支并过了、哪条指针还活着」寄存在上下文里；压缩点不由人挑，于是前沿连同它还指着的世界一起被摘要吃掉——解法不是把摘要写好，是让前沿本身提交进存储
- 主轴：上下文经济学
- 次轴：记忆与延续（机制在它那侧：entries / tasks / documents 都是先提交才可见，压缩只挪头、不删尾）
- 候选 leading word：the frontier has a second home
- 反直觉点在哪：以为压缩的代价记在「摘要质量」上，于是去调提示词、加 handoff 文档、把摘要写得更全；实际代价记在**所有权**上——只要「还差哪几张票」只活在模型上下文里，压缩点落在哪就是在赌。durable 侧压缩只缩小视图（older entries stay in storage，头是一条 `pi.compaction`），前沿可以现算：任务图每步有 checkpoint、票是提交过的状态、指针指向存储而不是对话
- 单边做法是谁：matt 的 implement-spec（communication only via context pointers + 手动 handoff：前沿靠提示词的纪律维持，而纪律管不着压缩点落在哪）
- 与邻居的分界：本轴 #04「指针不搬家」问的是指针**带多少**（密度）；本条问的是前沿**住在哪**（所有权）。「计划与路线」那条按压缩阈值给工作**切大小**，本条不切大小，只给进度换住处
- 来源：**人指定必收**（2026-10-16 人亲自提出，选料时不可淘汰）
