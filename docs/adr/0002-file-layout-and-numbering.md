# 灵感库的文件形态与编号规则

Status: accepted（决定于 [#8](https://github.com/JoeWest9966/md/issues/8)）

100 条灵感要住进一个仓库：多个 agent 会话并发地写、读者按批遇见它们、最后导出成 EPUB/PDF。三条约束决定形态：**写的人并行、读的人串行**（真闸门在**审读**那一侧：一批 = 一个审读员一个 fresh context 判得完的量，人只在成书后读一次，见 [ADR-0005](0005-full-autopilot-mode.md)）；**轴的名字会变**（同轴超 15 条要拆轴，边界还会吵）；**阅读次序会反复重排**（全书按自治成熟度阶梯排序）。所以：一条灵感一个文件、扁平放 `book/`；**编号是永久身份，次序是可改的编排，两者的真源分开住**。

## 布局

```
book/
  index.md            ← 次序的真源：一张全局有序表 + 书级 front matter
  037-fog-of-war.md   ← 一条灵感 = 一个文件（编号 + leading word 的 kebab）
  graveyard.md        ← 遗弃名单：烧掉的编号、曾用标题、弃因
notes/
  <axis>.md           ← 摘记池：一轴一文件，只追加，--- 分隔，无元数据
research/             ← 研究票的落盘产物
docs/adr/
```

- **一条灵感一个文件，扁平不按轴建目录**：轴会改名、会拆，编进路径的维度迟早撒谎。轴是 front matter 里的字段、`index.md` 里的列。
- **slug 取 leading word 的 kebab**（`037-fog-of-war.md`）：leading word 就是这条灵感的身份；中文标题住 front matter。
- **摘记池照抄 matt `writing-fragments` 的原生形态**：单文件、只追加、`---` 分隔、无 front matter、只有一个 H1 工作标题。`writing-shape` 规定成稿写进**另一个**文件——这里就是那个另一个文件，原始堆只读。

## 身份与编排

- front matter 只放身份：`number` / `title` / `axis` / `secondary_axis` / `leading_word`，加 `status`（`draft → reviewed → final`）。翻 `reviewed → final` 的是**书级冷读那一会话**，不是起草会话（[ADR-0005](0005-full-autopilot-mode.md)）。
- **编号**在**毕业**时发放，一次发一个轴段，永久、不复用、不回收。轴不参与编号（不做 1xx–8xx 分段：拆轴并轴那天，编号会集体说假话）。
- **次序**与编号无关，住在 `book/index.md`。编号不动，编排随便重排。
- **状态只在文件里，次序只在 index 里**：一个事实只住一处。index 不重复 status，也不重复 leading word。
- 弃掉的编号**烧掉**，进 `book/graveyard.md`（编号、曾用标题、弃因），文件删掉但 git 历史留着。选料时少写两条就**留空**——留空诚实，复用撒谎：复用的号会让旧引用指向另一条灵感，而且看不出曾经有过那一条。

## 并发

- 一批 = 一张写作票 + 一个 agent 会话 + 一个分支，3–5 条灵感。批的大小由**审读质量**定（一个审读员在一个 fresh context 里判 3–5 条，判词还引得出原句；再大，判词退化成形容词）——「由人的阅读预算定」那条口径已被 [ADR-0005](0005-full-autopilot-mode.md) 废掉（人只读成书后那一次）。
- **并发口径：跨轴并行、轴内串行**——默认同时 2 批，**硬顶 4 批**（阶梯四级各一批），**硬规则是不许两批同轴**。同轴并行会让轴内重复检测失灵（两批都看不见对方），而号段本来就按轴排队。新上限防的是：同轴并行、同一台阶上两批半成品互相拉扯（轴间配平判不出来）、并发写作批的合并冲突。
- **谁写谁锁定**：这批要建哪些文件，选料时就在票里列全，别人不许碰。**写作批绝不碰 `book/index.md`**——那一行由选料票一次写好。于是并行批之间零共享文件。
- 默认**串行**：一批写完、审完、合完，再开下一批。要并行就给每批一个 worktree；同一个工作树里两个 agent 各切分支是灾难。

## 地图与票

- 一轴一张**选料票**，产出「这一轴是哪 12 条 + 轴内次序 + 号段 + index 行」。
- 动笔时按**批**开写作票。一个审读员一个 fresh context 判不完的批就是坏批——批太大，判词退化成形容词，等于把质量关拆了。
- 不开 100 张「一灵感一票」：gh 2.23 没有 sub-issues，父子关系靠地图正文里手写的 task list；100 行手工账，且每关一张都要回去改地图。

## Considered Options

- **一轴一文件装 12 条灵感**（弃）：改一句 diff 一大片，两个 agent 同写必踩。
- **全书一个文件**（弃）：并发直接死，审读没法按条进行。
- **按轴分段编号（1xx–8xx）**（弃）：拆轴那天编号集体说假话，与「轴会变」直接冲突。
- **编号 = 阅读次序**（弃）：一次插队就是重命名 + 所有票和评论里的引用失准。
- **编号复用**（弃）：引用指向另一条灵感，且抹掉「曾经有过、后来弃了」这段事实。
- **用目录分组表达次序，或另开一份 `book/order.md`**（弃）：次序与轴的分组不是一回事——书按成熟度阶梯排、会跨轴；两个文件记两件事，不如一张表。

## Consequences

- 写一条灵感的顺序是：先毕业（选料票发号段 + 写好 index 行），再落地文件。
- `book/index.md` 由选料会话独占写入；写作批只新建自己名下的文件。
- 导出器（形态待定）从 index 头部取书级 front matter、从单篇 front matter 取身份，两边都不许有第二份真源。
- **没有生成器**（CLI 工具在范围外），index 是人肉维护的表——所以它必须短到能手工维护。这条反过来限制了哪些字段有资格进 index。
- 新增流程词进 `GLOSSARY.md` 时标 `档位: C（流程词，不进正文）`，免得被派生出书尾术语表。
